# Triage

Move incoming requests through a small state machine of triage roles. Requests arrive raw: a stakeholder's wish, a bug-in-requirement report, a change to an existing story. Items that `/split-backlog` produced are already refinement-ready; do not triage them.

Read `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md`. If missing, tell the user to run `/setup-requirements-repo`. Every comment posted to a tracker starts with:

```
> *This was generated by AI during triage.*
```

## Preflight (Pré-condições / Insumos Obrigatórios)

Check that these exist before doing anything else:

- `docs/agents/requirements-workflow.md`
- `docs/agents/issue-tracker.md`
- `docs/agents/triage-labels.md`
- the incoming request

If any of them is missing, **stop**. Do not invent, assume or reconstruct the missing data. Tell the user which inputs are missing and which skill produces each (`/setup-requirements-repo` for configuration, `/project-canvas` or `/create-product-vision` for the vision, `/split-backlog` for the backlog, `/spec-req` for specs, `/grill-with-docs` or `/to-questionnaire` for missing decisions); when several are missing or the way forward is unclear, tell the user to run `/wayfinder`.

Also read, when relevant: `<artifact-root>/01-vision/PRODUCT-VISION.md`; `<artifact-root>/shared/GLOSSARY.md`; `<artifact-root>/shared/DECISIONS.md`.

## Roles

Categories: `new` (does not exist yet), `change` (alters an existing US, CAP, GOAL, DEC or term).
States: `needs-triage`, `needs-info`, `ready-for-refinement`, `ready-for-po`, `out-of-scope`.

Each triaged item carries one category and one state. An unlabeled item goes to `needs-triage` first; `needs-info` returns to `needs-triage` when the requester replies. Flag unusual transitions and ask.

## Invocation

The user describes what they want in natural language: "show what needs attention", "look at request 3", "move 3 to ready-for-refinement".

## Show what needs attention

Three buckets, oldest first: unlabeled; `needs-triage`; `needs-info` with new activity. One line each. Let the user pick.

## Triage one item

1. **Gather context.** Read the item and its comments, prior triage notes (do not re-ask resolved questions), the vision, glossary, decisions and backlog. Run two checks: **redundancy** (does a story, CAP or DEC already cover it? Report where you looked; with the graph enabled, invoke `graph-sync` and run `req-graph.py query <artifact-root> "<request>"` instead of grepping; add the merged Graphify graph only for code or document coverage) and **prior rejection** (read `OUT-OF-SCOPE.md`).
2. **Classify and recommend.** State category and state with reasoning. For a `change`, invoke the `impact-analysis` skill and attach the report; a scope-changing change goes to `ready-for-po`. Wait for direction.
3. **Grill if needed.** Invoke the `grilling` skill and the `domain-modeling` skill and sharpen the item a round at a time.
4. **Apply the outcome:**
   - `ready-for-refinement`: write a durable brief (the need and outcome, linked IDs, confirmed rules, open DECs, impact for changes). Describe behavior, not files or screens.
   - `ready-for-po`: same, plus the decisions only the PO can make.
   - `needs-info`: post triage notes: what is established, and specific questions for the requester.
   - `out-of-scope`: say why; for a rejected `new` request add a short entry to `OUT-OF-SCOPE.md` (request, reason, date) and link it.

If the user says "move 3 to ready-for-refinement", trust them, confirm the action, skip grilling, and ask whether to write the brief.

## Next steps

End with `➡️ **Next step:** ...`.

- `new` and refinement-ready: `/spec-req` (bigger) or `/split-backlog` (a capability exists) or `/refine-request` (one story).
- `change` and refinement-ready: `/grill-with-docs` in change mode, then `/refine-request` on impacted stories.
- Too big or foggy: `/wayfinder`. Waiting on a person: `/to-questionnaire`.
